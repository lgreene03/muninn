# TESTING_STRATEGY.md

A system that claims determinism without proving it is making a marketing statement, not an engineering one. Muninn's tests are how the architecture's invariants are enforced.

## Layers

### 1. Unit Tests

**Scope.** Pure functions: validators, parsers, feature computers, window calculators, watermark advancers, serializers.

**Properties.** Fast (single-digit milliseconds), no IO, no Spring context, no Testcontainers.

**Naming.** `Method_state_expectedBehavior`. Example: `validate_blankSource_throwsValidationException`.

**Coverage target.** 100% line coverage for `shared-schema` validators and `feature-engine` computation code. Other modules: 80%+.

---

### 2. Contract Tests

**Scope.** Event schemas, public DTOs, configuration shapes.

**Properties.** Assert round-trip serialization. Assert backward and forward compatibility against golden files in `src/test/resources/golden/`.

**Required for any PR touching:**
- `shared-schema` records.
- Jackson configuration.
- Any field with `@JsonProperty`.

**Failure mode.** Mismatched golden file fails the build with a diff. Updating a golden file requires explicit reviewer sign-off.

---

### 3. Deterministic Replay Tests

**Scope.** The heart of the system. Required for any change to the feature engine, the event source, or the watermark logic.

**Mechanism.** A test fixture writes a known sequence of events into a Testcontainers Redpanda. The feature engine processes them and writes outputs to topic A. The fixture then resets engine state, re-runs over the same input, and writes outputs to topic B. The test asserts **byte-identical** equality of topic A and topic B.

Three variations are run:

1. **Same-JVM replay.** Live and replay back-to-back in one JVM.
2. **Cross-JVM replay.** Live in one JVM, replay in a fresh JVM after restart.
3. **Checkpointed replay.** Replay resumes from a mid-stream checkpoint; outputs after the checkpoint must match live outputs from the same watermark forward.

A failing determinism test is **never** quarantined or skipped. Fix the code or revert the change.

---

### 4. Integration Tests (Testcontainers)

**Scope.** Service-to-service wiring: ingestion → Redpanda → feature engine → MinIO/PostgreSQL → query-api.

**Stack.** Redpanda, PostgreSQL, MinIO via Testcontainers. Spring Boot context with `@SpringBootTest`.

**Properties.** Slower (seconds to tens of seconds). Run on every PR.

**Use cases.**
- End-to-end event ingestion.
- Feature emission to Redpanda and Parquet rollover to MinIO.
- Query-API responses against a known dataset.

---

### 5. Golden Dataset Tests

**Scope.** Feature-engine correctness against historical, hand-curated data.

**Mechanism.** A small, version-controlled dataset of real (or realistic synthetic) market events lives in `src/test/resources/datasets/`. Each feature has an associated expected-output file. Tests run the feature against the input and compare to the expected output.

**Updating the dataset.** Requires:
1. A reason in the PR description.
2. Re-running every downstream feature test to confirm only the intended outputs changed.
3. Reviewer sign-off.

This is how subtle correctness bugs are caught.

---

### 6. Failure / Restart Tests

**Scope.** Operational resilience.

**Scenarios.**
- Kill the feature-engine mid-stream. Restart. Assert no events lost, no events double-counted (idempotent recovery via checkpoint + offset tracking).
- Kill Redpanda for 30 seconds. Assert consumers reconnect, producers buffer-and-retry, no committed-but-unobserved events.
- Fill the disk to 95%. Assert backpressure, structured-log error, no data corruption.
- Corrupt a Parquet file. Assert the query-api reports an error and continues serving other queries.

**Properties.** Slow (tens of seconds to minutes). Run nightly or on demand, not on every PR.

---

### 7. Local Smoke Tests

**Scope.** End-to-end happy path on a developer machine.

**Mechanism.** `./scripts/smoke.sh`:
1. `docker-compose up -d --wait`.
2. Inject a known sequence of events via the ingestion API.
3. Wait for feature outputs.
4. Query the query-api for expected values.
5. Assert.

**Properties.** Runs in under 5 minutes from cold start. The contract from [LOCAL_FIRST_CONSTRAINTS.md](LOCAL_FIRST_CONSTRAINTS.md).

---

## Test Data Management

- **Synthetic data** for unit tests: small, generated, in-test.
- **Curated datasets** for golden tests: in `src/test/resources/datasets/`, version-controlled, small (≤ 1 MB each).
- **Replay datasets** for nightly tests: stored in MinIO, generated by a documented script. Never silently regenerated.

## What We Do Not Test

- Third-party library internals.
- Exchange API behavior (mock it; the adapter is tested against the contract, not against the real exchange).
- Performance under cloud-scale load (out of scope for MVP).

## Anti-Patterns

- **`@Disabled` without a linked issue.** Banned.
- **Tests that depend on wall-clock time.** Use a `Clock` abstraction injected from the test.
- **Tests that depend on iteration order of unordered collections.** Use sorted assertions.
- **Tests that test the mock instead of the system.** Test behavior, not interactions.
- **`Thread.sleep` for synchronization.** Use Awaitility with a bounded timeout.

## CI Requirements

- All unit + contract + integration tests must pass on every PR.
- Determinism tests are part of the PR suite.
- Failure/restart tests run nightly; failures open an issue automatically.
- Local smoke test runs in CI once per day against the published Docker images.
