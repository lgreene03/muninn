# 0011. Java 21 Sealed Interfaces for Canonical `MarketEvent` Hierarchy

- **Status:** Accepted
- **Date:** 2026-05-18
- **Deciders:** Data Engineer, Lead Architect
- **Related:** [DOMAIN_MODEL.md](../steering/DOMAIN_MODEL.md), [EVENT_SCHEMA_STRATEGY.md](../steering/EVENT_SCHEMA_STRATEGY.md), [CODING_STANDARDS.md](../steering/CODING_STANDARDS.md)

## Context

Muninn is an event-native streaming platform. Every piece of state and calculated output is derived from the immutable event log. We require a robust, compile-safe, and highly performant representation of our event schema.

In early streaming architectures, events were often represented as loosely typed JSON maps, generic key-value tuples, or a single massive, mutable Java class containing a large union of nullable fields.
1.  **Loosely Typed Maps:** Extremely prone to runtime bugs, missing fields, and lacks compile-time validation.
2.  **Generic Class with Nullable Fields:** Code consuming the class must constantly check which fields are populated, making business logic (such as VWAP calculations) highly fragile and difficult to test.
3.  **Inheritance Hierarchy:** Standard object-oriented polymorphism allows arbitrary subclassing, which prevents compile-time exhaustiveness checking and makes deterministic serialization difficult.

We need a solution that enforces:
*   **Immutability:** Events are historical facts and must never change once produced.
*   **Type Safety:** Stream consumers must know exactly what event type they are processing without casting.
*   **Compile-Time Exhaustiveness:** Event loops must handle all possible event types safely, alerting developers at compile time if a new event type is added but not handled.
*   **Clean Serialization:** Easy, zero-boilerplate translation to JSON (for Kafka streams) and Parquet (for MinIO warm archive files).

## Decision

We adopt Java 21 **sealed interfaces** combined with **record types** to represent the canonical `MarketEvent` hierarchy:

```java
public sealed interface MarketEvent permits TradeEvent, CandleEvent, OrderBookSnapshotEvent, FeatureComputedEvent {
    String eventId();
    String instrument();
    Instant eventTime();
}
```

Each permitted subtype is declared as a standard Java `record`, guaranteeing:
1.  **Immutability:** Subtypes are shallowly immutable out-of-the-box, with final fields and auto-generated boilerplate (`equals`, `hashCode`, `toString`).
2.  **Exhaustive Pattern Matching:** Developers can use Java 21's enhanced switch pattern matching in stream processors:
    ```java
    switch (event) {
        case TradeEvent t -> processTrade(t);
        case CandleEvent c -> processCandle(c);
        case OrderBookSnapshotEvent o -> processSnapshot(o);
        case FeatureComputedEvent f -> processFeature(f);
        // No 'default' branch required; compiler enforces exhaustiveness!
    }
    ```

For JSON serialization over Redpanda/Kafka, we utilize Spring Kafka's `JsonDeserializer` with custom type mappings, translating these immutable records directly to JSON payloads.

## Consequences

**Easier:**
*   **Compile-Time Safety:** Adding a new event type without updating switch statements immediately halts compilation, preventing silent runtime production crashes or unhandled event drops.
*   **Readability:** Zero boilerplate. Business logic is extremely readable, expressive, and safe.
*   **No Casting:** Pattern matching binds the typed record variables automatically, eliminating unchecked casts.

**Harder:**
*   **Schema Evolution:** Modifying or adding subtypes requires updating all code blocks implementing the sealed switch branches in the same commit. This forces schema modifications to be highly deliberate.
*   **Deep Immutability:** Java records are shallowly immutable. Developers must ensure that nested collection fields (such as order book price levels) are wrapped in unmodifiable collections (e.g., `List.copyOf`).

## Alternatives Considered

*   **Lombok-Annotated Standard POJOs:** Rejected. Lacks the native runtime and compiler guarantees of Java records and sealed classes, and introduces external annotations that can fail across JVM updates.
*   **Flat Event Class with Optional Fields:** Rejected. Promotes fragile code with nested null checks, increasing cognitive load and testing complexity.
*   **Protocol Buffers / Avro Native classes:** While excellent for cross-language serialization, Avro classes generated by plugins introduce significant boilerplate, make custom pattern matching clumsy, and complicate unit-testing without active schema registry deployments in MVP.
